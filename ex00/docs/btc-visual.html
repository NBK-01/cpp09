Nearest-Date Lookup price a wallet on any day, even days the database never recorded

The program owns a price book: a date → exchange-rate table loaded from data.csv. You hand it lines like 2011-01-09 | 5, and for each one it multiplies your amount by that day's rate. The twist: if your date isn't in the book, it must use the closest earlier date — and an std::map makes that a single lookup.

input
2011-01-03 | 3 2011-01-09 | 5 2001-42-42 2012-01-11 | -1
output
2011-01-03 => 3 = 0.9 2011-01-09 => 5 = 1.6 Error: bad input => 2001-42-42 Error: not a positive number.
known rate / valid output your input line rejected line

Every line is handled independently — one bad line never stops the rest.

flow

The whole program in four moves

Two files in, one loop out. main() just wires it together and catches any fatal error (a missing file, an empty database) so the program dies cleanly with one message.

1

Check the arguments

Exactly one argument — the input file. Anything else prints the usage error and exits.

2

loadDB("data.csv")

Read the price book once into a sorted std::map<string, float>. Skip the header, skip any junk line, and only fatally fail if the whole database ends up empty.

3

processInput(argv[1])

Read the input file line by line. Split each on |, validate the date, classify the value, then look up the rate and print date => value = product.

4

Report, never crash

Bad lines print an error and continue. Only a bad program state (no file, empty DB) throws and stops everything.

01

Why an std::map, keyed by the date string

A std::map keeps its keys permanently sorted. Dates written as YYYY-MM-DD sort chronologically as plain text — "2011-01-03" < "2011-01-09" is true both as strings and as dates. So the map is a sorted timeline for free, and finding a neighbour becomes one O(log n) jump instead of a scan.

data.csv, once parsed into the map

2011-01-03 → 0.3 2011-01-07 → 0.32 2012-01-11 → 7.1

Loading skips the date,exchange_rate header, trims whitespace, splits on the comma, and drops any row whose date is malformed or whose rate won't parse.

02

The heart of it: lower_bound and one step back

You ask for 2011-01-09, but the book only knows the 3rd, the 7th, and next year's 11th. lower_bound(date) returns the first entry not less than your date — that's 2012-01-11. That's too late, so we step back one (--it) to land on 2011-01-07, the closest earlier day. Its rate, 0.32, is the answer.

a

Exact hit?

it->first == date → use that rate directly. (e.g. 2011-01-03 returns 0.3 with no stepping.)

b

Landed past the end or in the middle?

Step back once with --it to the closest earlier date. Here: 2012-01-11 → back to 2011-01-07.

c

Already at the very first entry?

No earlier date exists — the query predates the whole book. That's a bad line: Error: bad input => …

O(log n)

One binary search does it. Because the map is always sorted, lower_bound is a logarithmic jump — no matter how many thousands of days the price book holds.

03

Two gates every input line must pass

Before any lookup happens, a line is checked twice: is the date real, and is the value in range? These are split so the error message can be precise about which one failed.

Gate A — isValidDate()

Length must be exactly 10, dashes at positions 4 and 7, digits everywhere else. Then month 1–12, day ≥ 1, and day ≤ the real length of that month — with February getting 29 days on a leap year (÷4 but not ÷100, unless ÷400). So 2001-42-42 and 2011-02-29 both fail.

Gate B — parseVal() sorts the value into four buckets

V_OK
0 ≤ v ≤ 1000

Valid. Multiply by the rate and print the result.

V_NEG
v < 0

Error: not a positive number.

V_BIG
v > 1000

Error: too large a number.

V_BAD
not a number

Empty or garbage. Error: bad input => …

The value is parsed with strtod; if any leftover character remains after the number (end != '\0'), it's V_BAD. An enum return keeps the caller's branching clean.

  line = trim(line);
  if (line.empty()) continue;

  str date = trim(line.substr(0, comma));

02 The nearest-date lookup — BitcoinExchange::getRate
std::map<str,float>::const_iterator it = _db.lower_bound(date);
if (it != _db.end() && it->first == date)
  return it->second;             // exact hit
if (it == _db.begin())            // nothing earlier exists
  throw std::runtime_error(ERR_BAD);
--it;                            // step to the closest earlier date
return it->second;
03 Classify one input line — parseVal (utils.cpp)
double v = std::strtod(c, &end);
if (end == c || *end != '\0') return V_BAD; // junk
if (v < 0)    return V_NEG;
if (v > 1000) return V_BIG;
out = static_cast<float>(v);
return V_OK;

size_t bar = line.find('|');

notes

The edge cases that trip people up

!

Query older than the whole book

lower_bound returns begin() and it's not an exact match → treated as bad input, because there's no earlier rate to borrow.

!

Line with no | separator

Printed as Error: bad input => <line> and skipped — the split simply can't happen.

!

Value exactly 0 or exactly 1000

Both valid — the bounds are inclusive. 0 is not negative; 1000 is not "too large".

!

Two rate parsers on purpose

parseVal range-checks input values (0–1000); parseRate accepts any DB rate without bounds. Same idea, different rules.
