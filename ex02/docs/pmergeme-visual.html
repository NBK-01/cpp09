Merge-Insertion Sort the Ford–Johnson algorithm, and exactly how our code runs it

Merge-insertion sorts by making as few comparisons as it possibly can. It pairs elements up, recursively sorts the winners into a spine, then folds the losers back in — but always searching a window whose size is bounded, and always in an order (the Jacobsthal order) that keeps those windows just under a power of two.

Recurse on the winners

The a values are themselves an unsorted list. Sort them by calling the whole algorithm again — this recursion is what makes it merge-insertion and not plain insertion sort. When it returns, the main chain is sorted and becomes the spine everything else folds into.

stage 03

Line the pend up behind the spine

Each winner still owns a partner. Re-read them in the sorted order of the main chain, so pend[j] is the smaller partner of main[j]. This alignment is the whole game: it means pend[j] is guaranteed ≤ main[j], which later lets us cap its search at that partner.

Seed with b₁

stage 05

Insert the rest in Jacobsthal order — each search bounded by its partner

The remaining pend elements go in the order 3, 2, 5, 4 (1-indexed) — our jacobOrder() returns the 0-based indices 2, 1, 4, 3. For each one, binary-search only the slice [start, partner) of the chain, since it can never land past its partner. That capped window is why the comparison count stays optimal.

why

Why the Jacobsthal order

Insertions push elements rightward, so a partner's live index keeps moving. The Jacobsthal numbers 1, 3, 5, 11, 21… (each = previous + 2×the one before) pick the insertion order so that every element, at the moment it is inserted, faces a window of size 2ᵏ − 1. Binary-searching a 2ᵏ−1 window costs exactly k comparisons with none wasted — that is the whole trick behind the minimal comparison count.

Each stage in src/PmergeMe.cpp

The core is one templated function, so std::vector and std::deque run the identical logic. Here is how the stages above map onto it.

01 Pair & split — larger to bigs, smaller into a value-keyed map
if (a < b)
  std::swap(a, b);        // a = larger, b = smaller
bigs.push_back(a);
partners[a].push_back(b); // keying by value keeps every b ≤ its a
02 Recurse on the winners
fordJohnson(bigs);         // bigs comes back ascending = the spine
03 Re-read partners in sorted-spine order
for (size_t i = 0; i < bigs.size(); ++i) {
  std::vector<T> &q = partners[bigs[i]];
  pend.push_back(q.back());  // pend[i] is the partner of bigs[i]
  q.pop_back();
}
04 Seed b₁, and track each partner's live index in aPos
Cont chain(bigs.begin(), bigs.end());
for (size_t j = 0; j < bigs.size(); ++j)
  aPos[j] = j;                       // where bigs[j] currently sits
chain.insert(chain.begin(), pend[0]); // b1 → front, always
for (size_t j = 0; j < aPos.size(); ++j)
  aPos[j] += 1;                     // everyone shifted right by one
05 Jacobsthal order + bounded binary insertion
std::vector<size_t> order = jacobOrder(pend.size());
for (size_t o = 0; o < order.size(); ++o) {
  size_t j = order[o];
  Iter last = chain.begin() + aPos[j];  // ← the bound: partner's slot
  Iter it   = std::lower_bound(chain.begin(), last, pend[j]);
  size_t p  = it - chain.begin();
  chain.insert(it, pend[j]);
  for (size_t t = 0; t < aPos.size(); ++t)
    if (aPos[t] >= p) aPos[t] += 1;   // keep every index live
}
· How jacobOrder() builds 2,1, 4,3, 10..5 …
size_t prevPeak = 1, jPrev = 1, jCurr = 3;
while (prevPeak < m) {
  size_t peak = (jCurr > m) ? m : jCurr;
  for (size_t p = peak; p >= prevPeak + 1; --p) {
    order.push_back(p - 1);       // descend each Jacobsthal group
    if (p == prevPeak + 1) break;
  }
  if (peak >= m) break;
  prevPeak = jCurr;
  size_t nextJ = jCurr + 2 * jPrev;  // J(n) = J(n-1) + 2·J(n-2)
  jPrev = jCurr; jCurr = nextJ;
}
06 Straggler — unbounded, no partner to cap it
if (hasStraggler) {
  Iter it = std::lower_bound(chain.begin(), chain.end(), straggler);
  chain.insert(it, straggler);
}
proof

How close to optimal

Worst-case comparisons (6000 shuffles per size) vs. F(n) = Σ ⌈log₂(3k/4)⌉, the proven minimum for merge-insertion. We land exactly on it for most sizes and at most +2 over for a band of mid-sizes — because we bound each search by the partner's live index, which is occasionally 2ᵏ instead of the ideal 2ᵏ−1. Near-optimal, always correct, and well under plain binary-insertion sort.
